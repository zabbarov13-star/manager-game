## 1. Подтверждённая исходная установка

Сведения предоставлены владельцем; удалённого SSH-подтверждения из этой рабочей сессии нет:

| Компонент | Существующее значение | Решение |
|---|---|---|
| Игровая служба | `manager-online.service`, active, enabled | Сохранить имя, пользователя и автозапуск |
| Код | `/opt/manager-online/current` | Обновлять исходную установку через проверенный release/symlink |
| Запуск | `/opt/manager-node/bin/node online/server.cjs` | Сохранить точку входа; Node v24.22.2 не обновлять |
| Пользователь | `manager-online` | Сохранить права, не запускать игру от root |
| Игровой HTTP | `127.0.0.1:8080` | Единственный авторитетный сервер комнат для обоих клиентов |
| SQLite | `/var/lib/manager-online/rooms.sqlite`, WAL | Сохранить путь, схему, записи и историю replay |
| Известные таблицы | `online_rooms`: 10, `replay`: 228 на момент проверки владельцем | Не удалять/обнулять; числа не являются постоянным критерием при живом сервере |
| Копия | `/root/manager-backups/rooms-before-update.sqlite`, integrity_check=ok | Сохранить как исходную копию; дополнить проверкой реального открытия/восстановления и свежей копией перед переключением |
| APK/Web | `https://95-181-169-84.sslip.io` | Сохранить origin, маршруты и совместимость старых APK |
| «Смайлокрут» | отдельный Docker, `127.0.0.1:18080` | Не менять контейнеры, данные и маршруты |
| HTTPS | существующий Caddy | Сохранить общий ingress; второй Caddy не запускать |

Node 18 общего окружения не является runtime игры: у неё уже есть собственный Node 24.22.2. Требование приложения `>=24.22.1 <25` ему соответствует по версии; наличие `node:sqlite`, права и фактические хеши файлов ещё проверяются на хосте без изменений служб.

## 2. Что найдено в коде

- `online/server.cjs` владеет SQLite комнат, очередью транзакций, серверным броском кубиков и replay. Старый протокол использует seat bearer token, `Idempotency-Key`, `requestId`, `gameRevision`; Telegram-сессия его не заменяет.
- APK `packaging/android/.../MainActivity.java` загружает встроенный HTML под прежним HTTPS-origin; запросы комнат уходят на этот же origin. Подмена корня сайта Telegram-страницей потребовала бы initData там, где его нет. Корень APK/Web не менять.
- `telegram/server.cjs` **сейчас создаёт собственный room server** через `telegram/rooms.cjs` и `rooms.sqlite` рядом с Telegram-базой. Одинаковый исходный код не означает общий процесс или общие комнаты. Этот режим нельзя запускать как итоговую архитектуру на найденном VPS.
- `telegram/rooms.cjs` переиспользует исходный HTTP-сервер, но подставляет расширенный engine и серверную проверку косметики. Дополнительные JSON-поля анимации совместимы по принципу расширения ответа; проверка прав должна остаться серверной.
- Простая замена `online/dist/engine.cjs` Telegram-сборкой **небезопасна**: без доверенного HTTP-адаптера нельзя принимать клиентское `telegramCharacterVerified` или `X-Manager-Verified-Cosmetic` за разрешение. В старом APK также нет новых изображений: успешная игра не доказывает отображение новой косметики его старой версией.
- PeerJS/WebRTC — отдельный путь игры, отличный от HTTP-комнат. Проверка SQLite/HTTP не доказывает смешанную P2P-партию со старым APK.

## 3. Целевая архитектура

| Вход/маршрут | Куда направлять | Что хранит/делает |
|---|---|---|
| Прежний origin `/`, APK/Web assets | существующий `manager-online:8080` | Прежний интерфейс и протокол APK |
| Прежний origin `/api/rooms` и `/api/rooms/*` | тот же `manager-online:8080` | Все комнаты, состояние партий и replay |
| Telegram origin `/api/rooms` и `/api/rooms/*` | **тот же** `manager-online:8080` | Те же комнаты/seat tokens/команды; без второго процесса комнат |
| Telegram origin остальные публичные пути | отдельный Telegram-адаптер, `127.0.0.1:8443` | Mini App assets, проверенный initData, профили, owner, Stars webhook, отключённый AdsGram |
| Внутренняя проверка косметического права | приватный интерфейс Telegram-адаптера | Только проверка ticket/character и актуальности права; не игровая экономика |

Предлагаемый Telegram-origin: `https://manager.95-181-169-84.sslip.io`. Это отдельный интерфейс и монетизация над **одним** сервером комнат, а не второй экземпляр игры/БД комнат. Поддомен оправдан тем, что сохраняет APK-root, старый service worker и browser storage и не требует переписывать абсолютные пути Mini App. Схема с `/mini-app/` на старом origin потребует отдельной переработки путей и проверки старого service worker; её не выбирать автоматически.

Предлагаемый каталог адаптера `/opt/manager-telegram`, служба/Compose-project `manager-telegram`, данные `/var/lib/manager-telegram/telegram.sqlite`, резервные копии `/var/backups/manager-telegram`, секреты в отдельном защищённом env. Это **проектные значения**, их свободность и права на VPS не проверены. Адаптер не открывает `/var/lib/manager-online/rooms.sqlite` и вообще не создаёт свою `rooms.sqlite`.

Внутренний verifier лучше вынести на отдельный Unix socket с ограниченной группой и аутентификацией; он не должен публиковаться Caddy. Если выбран loopback HTTP, нужны отдельная межсервисная аутентификация и жёсткий запрет публичного маршрута. Bot token, initData и финансовая БД остаются только у адаптера; игровому серверу достаточно ответа о косметическом праве. Старый публичный `/api/cosmetics/verify` не считать готовым защищённым межсервисным контрактом.

## 4. Необходимые локальные изменения до развёртывания

1. Добавить в Telegram-сервер явный режим без локальных комнат. В нём не создавать/открывать room DB, не запускать cleanup комнат, а ошибочную прямую маршрутизацию `/api/rooms` завершать понятной ошибкой. Существующий автономный режим оставить для тестов. Отдельно проверить, что рестарт адаптера не останавливает общую партию.
2. Дать существующему `online/server.cjs` необязательное расширение для косметики/AnimationEvent без Telegram-зависимостей в правилах. По умолчанию сохранить исходное поведение и запуск. Собирать серверное расширение отдельно от Telegram HTML; не заменять APK assets и не требовать initData от старого клиента.
3. Реализовать доверенный verifier: у create/join/appearance проверять ticket, при start перепроверять право ожидающих игроков. Клиентские флаги/внутренние заголовки сбрасывать на входе. Старые команды без метаданных работают без обращения к Telegram. Уже допущенную партию не прерывать при истечении временного права.
4. Сетевую проверку выполнять **до BEGIN IMMEDIATE**, с коротким таймаутом и проверкой актуальности room revision при записи. Не держать write-lock и общую очередь во время недоступного Telegram-сервиса. При его отказе новые неподтверждённые премиальные запросы отклоняются с возможностью повтора; обычные APK-ходы и текущие партии продолжаются. Повтор подтверждённой команды обслуживается из replay даже при недоступном verifier.
5. Сохранить путь/формат команд, байты тела при проксировании, Authorization и `Idempotency-Key`, `requestId`, текущие токены и replay. Не переназначать seat IDs и не менять тело старой команды по пути: иначе изменится её replay signature. Не передавать animation frames по сети.
6. Отдельно подготовить Caddy-сопоставления **точных** room paths к 8080 и остальных Telegram paths к 8443. Старый origin и «Смайлокрут» оставить буквально прежними. В текущем `caddy-guard.cjs` разрешён только один upstream 8443: для этого плана guard и его тест реальным Caddy нужно адаптировать, а не обходить.
7. Переделать Compose, runtime-check и backup-инструкции для adapter-only режима. Текущие `compose.host.yaml`/`vps.cjs apply` рассчитаны на автономную Mini App с собственными комнатами и **не подходят** для этого обновления. Не создавать managed-marker для обхода отказа legacy-инсталляции.

Эти изменения перечислены для реализации после рассмотрения архитектуры; в текущем шаге runtime не переписан и новая схема не объявляется готовой к применению.

## 5. Проверки и критерии допуска

**PASS локально, синтетическая БД:** `node --test telegram/tests/shared-room-compat.test.cjs` после Telegram build. Исходный сервер/engine собран без Telegram-патчей в отдельный временный каталог с нормализацией CRLF. Проверено последовательное использование **одной** SQLite: старый engine → расширенный → старый. Сохранились seat tokens, game state, revision, исходные строки replay и байтовое содержимое сохранённого room JSON при чтении/повторе. Повтор старого HTTP-запроса после обновления и нового после отката возвращает исходный ответ без двойного хода; SQLite integrity_check=ok. Рабочая база и её копия не читались. Это подтверждает осуществимость, но не окончательную совместимость развернутой версии.

**Обязательно до разрешения переключения:**

- Сверить unit/env-пути без вывода значений секретов, фактический `readlink current`, commit/хеши server/engine, Node SQLite, Caddy disk/active config, владельца файлов, свободные RAM/диск, существующие таймеры и порт 8443. Не использовать состояние владельца как разрешение SSH/write.
- На отдельной копии настоящей БД проверить схему, JSON старых комнат и открытие новым/прежним кодом; не посылать действия в исходные 10 комнат. Старые просроченные комнаты могут штатно удаляться cleanup, поэтому испытания вести только на копии с контролем изменений; рабочие записи не переинициализировать.
- В изолированном локальном/тестовом контуре: один room process, оба origins, две разные версии клиента, create/join/ready/start/roll/buy/chat/leave/reconnect; одни state/balance/property/revision; повтор потерянного ответа через другой origin без двойного действия.
- Смешанная партия реального старого APK и Mini App; затем PeerJS со старым/новым хостом, восстановление хоста, watermark/eventId/sequence. Старый APK может показать базовый образ; выпуск новой APK-косметики согласовывать отдельно.
- Подделка metadata/headers/tickets, таймаут verifier, истечение в лобби/после старта, рестарт адаптера, HTTP replay при недоступном verifier; отсутствие второй room DB и финансовой логики в общем engine.
- Профили/owner/Stars webhook и история отдельно от игровых token/replay. AdsGram и Stars остаются OFF при первом запуске до соответствующей живой проверки/разрешения. Никаких реальных платежей и изменений бота в этом плане.

**BLOCKED сейчас:** нет прямого доступа/хешей/копии реальной БД; adapter-only разделение и защищённый verifier ещё не реализованы; смешанная APK/Telegram приёмка не выполнена. Предыдущие 108/PeerJS тесты не заменяют новые смешанные сценарии.

## 6. Порядок обновления после отдельного разрешения

1. Зафиксировать ожидаемые хеши, конфигурации и точные пути; собрать и проверить два отдельных неизменяемых артефакта из PR, без секретов. Подготовить предыдущий release и совместимость отката. Не пользоваться старым CI deploy автоматически: его whitelist/archive сейчас не содержит Telegram-адаптер и общий расширенный engine.
2. Проверить существующую копию, восстановить её в отдельный каталог и прогнать проверки выше. Сохранить прежние unit/env/Caddy-конфигурации приватно. Не переносить единственную копию и не менять её права в публичные.
3. Подготовить каталог/пользователя/данные только Telegram-адаптера, установить его с платежами и рекламой OFF. На loopback проверить identity/health и отсутствие rooms.sqlite. Этот шаг разрешается только вместе с конкретным планом. Общую игру пока не переключать.
4. В согласованное короткое окно остановить **только** `manager-online.service`, убедиться в отсутствии оставшегося writer, сделать свежий согласованный SQLite backup, проверить integrity и восстановление. WAL включать через SQLite backup API; обычное копирование одного живого `.sqlite` недопустимо. Не удалять WAL/SHM. Сохранить все другие найденные данные и прежний release.
5. Атомарно переключить `/opt/manager-online/current` на проверенный release общего сервера, сохранить `ROOM_DATABASE=/var/lib/manager-online/rooms.sqlite` и порт 8080; запустить ту же службу/пользователя. Никаких DROP/пересоздания таблиц или переезда базы. Проверить local/старый HTTPS health, APK-протокол и восстановление согласованной тестовой комнаты. При ошибке перейти к откату.
6. Добавить только Telegram host route в действующий Caddy; semantic guard должен подтвердить неизменность остальных sites/TLS/listeners, затем validate и reload (не restart). Проверить HTTPS нового origin, маршруты 8080/8443 и работоспособность старого сайта/«Смайлокрута». При отсутствии безопасного способа выделить host route остановить этот шаг и пересмотреть план.
7. Проверить настоящий Mini App и смешанную партию. Настройки webhook/меню/Main Mini App — отдельное согласование после подтверждения личности/Telegram-среды бота. Реальные платежи и вывод Stars не входят в разрешение на серверное обновление.
8. Настроить и проверить приватные раздельные backups комнат/Telegram DB плюс внешнее хранение; данные двух сервисов не считать атомарным снимком без согласованной остановки/барьера. Мониторить ошибки без токенов, health, память, задержки и число процессов комнат.

Точное время окна определить только после размера БД, пробного восстановления и измерения рестарта на копии. Не обещать безостановочное обновление одного writer.

## 7. Откат

- **Код общего сервера:** вернуть прежний symlink и запустить ту же `manager-online.service`. Оставить текущую игровую SQLite и replay; не возвращать автоматически базу к старой копии и не терять подтверждённые ходы. Это допустимо лишь после проверки обратной совместимости на копии.
- **Telegram-адаптер:** остановить/откатить только его службу, убрать только его новый host route, если он ещё соответствует записанному нашему хешу. Не перетирать параллельные изменения администратора Caddy. Старые APK/8080 и «Смайлокрут» продолжают работать.
- **Данные:** при повреждении/необратимой миграции остановить только writer игры, сохранить текущую БД+WAL/SHM как evidence, согласовать отдельный recovery из проверенной копии с учётом новых ходов/платежей. Автоматического восстановления старых данных поверх рабочих нет.
- После отката проверить прежний HTTPS/API, текущие комнаты, токены, повтор команды без двойного действия и protected service. Отчёт PASS допускается только после фактической проверки, которой пока не было.
