# Существующий общий VPS: сначала инвентаризация

Текущие факты и ограничения: [ACCESS-STATUS.md](ACCESS-STATUS.md). Скрипты не дают разрешение на изменение сервера. Пользователь требует согласовать конкретный план до запуска. Не запускать `telegram/staging/compose.yaml` на общем VPS: он публикует второй Caddy на 80/443 и предназначен для выделенного стенда.

## 1. Проверка без изменения служб

Скопировать `inspect-vps.cjs`, `public-client.cjs`, `bot-check.cjs`, `caddy-guard.cjs` и `telegram/tests/stable-signatures.json` с сохранением структуры `telegram/` в приватный временный каталог на VPS. Никаких токенов для inventory не нужно. Node 18.20.4 подходит.

```sh
sudo node telegram/deploy/inspect-vps.cjs --out /root/manager-vps-inventory.local.json
```

Это только чтение Docker (включая остановленные контейнеры), mounts, релевантных systemd units, слушающих портов, хешей Caddy и поиска каталогов в /opt, /srv, /var/www, /home, /root. Содержимое env, строки SQLite, командные строки контейнеров и сообщения журналов не выводятся. Отчёт содержит внутренние пути, хранить приватно, не коммитить. Поиск ограничен глубиной/числом каталогов; неизвестные каталоги, truncated и предупреждения требуют ручного уточнения. База вне найденных путей не считается отсутствующей. Inventory сам не делает резервных копий и ничего не перезапускает.

Установить связь origin → Caddy upstream → контейнер/процесс → compose/systemd → данные. Подтвердить владельца 8080, а не предполагать его по номеру. Проверить scoped logs после редактирования секретов; их текст скрипт намеренно не копирует. Проверить существующие файлы сохранений и браузерный прогресс. Для неизвестной legacy-установки нужен отдельный адресный план адаптации и backup/restore; контроллер ниже откажется автоматически её обновлять или дублировать.

## 2. Локальная подготовка приватного пакета

На Windows из чистой закоммиченной ветки PR, используя Node 24:

```sh
node telegram/deploy/package.cjs
node telegram/deploy/prepare-env.cjs
```

В игнорируемом `telegram/deploy/out/` появятся tar из `git archive`, release.json с commit/SHA-256 и **приватный** manager.env. Исходный `telegram/.env` не меняется. Архив исключает игнорируемые файлы; упаковщик отказывается от отслеживаемых env/баз и совпадений с локальными секретами. manager.env не загружать в GitHub/artifacts. Передавать только по защищённому каналу. Если утверждён старый origin, сформировать env с этим доменом через `prepareEnv(text,{domain})`; apply также заново формирует его по плану. Не менять TELEGRAM_ENV по имени бота.

## 3. План для известной управляемой установки

На VPS, **без запуска apply**:

```sh
sudo node telegram/deploy/vps.cjs plan --inventory /root/manager-vps-inventory.local.json --manifest /root/manager-release/release.json --root /opt/manager-mini-app --domain manager.95-181-169-84.sslip.io --mode update --out /root/manager-plan.local.json
```

Пути/домен здесь пример, а не решение о переносе текущей игры. `BLOCKED` для неизвестной старой установки — ожидаемый результат. Не обходить его созданием `manager-deployment.json`. `--mode new` также блокируется при обнаружении прежнего «Менеджера». Пока фактическая установка не найдена и не согласован её перенос/обновление, автоматическое развёртывание на этом VPS **не готово к применению**.

Для уже управляемой этим контроллером установки план фиксирует образ/архив, хеш inventory, Caddy, origin, отдельные данные и службу. Требуется host Caddy с согласованной дисковой/активной конфигурацией; контейнерный ingress, environment expansion и относительные file imports требуют адаптации вручную. Нельзя автоматически отнимать существующий чужой route.

## 4. Только после согласования точного плана

```sh
sudo node telegram/deploy/vps.cjs apply --plan /root/manager-plan.local.json --archive /root/manager-release/manager-COMMIT.tar --env-file /root/manager.env --approve EXACT_APPROVAL_HASH --allow-shared-caddy
```

Контроллер проверяет актуальность плана, архив, владельца каталога/службы, неизменность всех маршрутов/настроек Caddy за пределами точного host matcher «Менеджера». Используется одна служба `manager-mini-app`, Node 24 внутри контейнера, только `127.0.0.1:8443`, приложение внутри на 8090; собственного Caddy нет. Общий Node, Docker и Caddy не обновляются. Runtime ограничен 0.5 CPU/512 MiB, dropped caps, read-only rootfs; сборка Docker может потреблять дополнительные ресурсы — перед разрешением оценить запас CPU/RAM/диска и окно работ.

До остановки прежнего **управляемого** экземпляра проверяются образ, native SQLite и личность бота read-only. Затем останавливается только его служба; полный data tar сравнивается с источником, восстанавливается в отдельный каталог, снова сравнивается, обе SQLite проверяются на integrity. Все прочие файлы данных также входят в копию. При незнакомых ссылках/специальных файлах применяется отказ, а не обход чужих данных. Для старой схемы сначала нужен отдельный тест миграции. Рабочую БД никогда не заменяют автоматически резервной копией.

После запуска проверяются local health, HTTPS health новой Mini App (включая выключенные Stars/Ads) и доступность защищённого сервиса на 18080. Это не заменяет функциональную ручную проверку «Смайлокрута». Caddy только validate + scoped reload после semantic guard. Активная API-конфигурация должна совпасть с диском; сторонние изменения не перетираются. BotFather, webhook и финансовые API этот apply не изменяет.

При ошибке выполняется ограниченный откат кода/config; данные сохраняются, следы транзакции остаются. Неуспешную первую попытку нельзя повторять вслепую: остатки требуют проверки владения. Реальный apply/автооткат на данном VPS пока **BLOCKED**, локальные тесты не считаются его успешным выполнением.

## 5. Последующий откат и резервирование

```sh
sudo node telegram/deploy/vps.cjs rollback --root /opt/manager-mini-app
# Проверить выданный план, затем отдельно подтвердить его hash:
sudo node telegram/deploy/vps.cjs rollback --root /opt/manager-mini-app --approve EXACT_APPROVAL_HASH
```

Откат переключает только код на предыдущий управляемый release, сохраняет текущие базы/платежи/секреты и маршруты Caddy. Если схема не обратно совместима, нужен адресный план; не понижать БД автоматически. Первой legacy-установке этот механизм не приписывает несуществующую историю.

Регулярные парные SQLite snapshot/restore и защищённый timer подготовлены отдельно в [RELEASE-RUNBOOK.md](../RELEASE-RUNBOOK.md). Timer **не устанавливается автоматически**; после утверждения реального data directory настроить его и защищённую внешнюю копию, проверить восстановление, мониторить ошибки и свободное место. Не удалять данные/тома и не запускать docker prune/down для общего хоста.

## 6. Telegram и приёмка

На Node 24 с приватным env: `node --env-file=telegram/deploy/out/manager.env telegram/deploy/bot-check.cjs --probe-environments`. Только getMe/getWebhookInfo/getChatMenuButton; токены, ID и исходные ошибки не выводятся. PASS_IDENTITY подтверждает лишь личность, а не готовность webhook или платежей. Node 18 не поддерживает --env-file: использовать env_file изолированного контейнера, не source неизвестного env в shell.

После HTTPS и согласования настроек использовать dry-run `setup-bot.cjs`, затем отдельно разрешённый apply. Указать Main Mini App в BotFather. Пройти настоящий вход, owner, второе устройство, PeerJS и тестовый Stars-поток. AdsGram держать OFF до доверенного серверного подтверждения. Production-платежи, возвраты, Fragment и изменение действующего бота требуют отдельного разрешения.

CI проверяет Node 18 инструменты, общую Compose-конфигурацию, реальный Caddy adapter/validate и сборку приложения с Node 24. Bootstrap образа запускается без внешней сети, с read-only rootfs: проверяет HTTP UI/health, отказ анонимному профилю и integrity обеих SQLite на временном tmpfs. Реальные секреты/платежи для него не нужны. Эти проверки не выдают PASS за фактический deploy на VPS или пользовательскую приёмку.
