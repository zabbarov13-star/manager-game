# Подготовка тестового стенда, обновление и откат

Production и действующий бот не изменены, PR №5 не слит. Бот @ManagerGameTestBot и локальный токен уже подготовлены, но Telegram API пока недоступен из рабочей среды. На общем VPS найден прежний публичный клиент «Менеджера»; SSH root отклонён. Актуальный порядок — сначала [инвентаризация существующей установки](deploy/README.md) и согласование плана. Compose ниже с портами 80/443 предназначен только для выделенного стенда; на общем VPS его не запускать. Ниже подготовленные действия, а не отчёт о развёртывании.

## 1. Локальный HTTPS-контур

Из корня репозитория:

```sh
node telegram/staging/init-local.cjs
node telegram/build.cjs
node --env-file=telegram/.env telegram/staging/check.cjs
```

init-local дописывает отсутствующие настройки и генерирует секреты в игнорируемом `telegram/.env`, существующие значения не меняет. Локальные TLS-файлы находятся в игнорируемом `telegram/data/staging/tls`; приватный ключ не попадает в Git или образ. Сертификат действует 14 дней, не устанавливается в доверенные ОС и не является публично доверенным сертификатом. Неполная пара ключ/сертификат не перезаписывается.

После добавления тестового токена и контакта поддержки можно запустить:

```sh
node --env-file=telegram/.env telegram/staging/local.cjs
```

Адрес — `https://localhost:8443`, привязка только loopback; базы только в `telegram/data/staging`. Проверка TLS с доверенным именно этому сертификату клиентом выполнена автотестом. Это не публичный Telegram-стенд и не подтверждение входа через настоящий клиент. Без токена сервер намеренно не запускается; обхода initData нет. HTTP разрешён официальной тестовой средой Telegram, но публичный стенд ниже использует HTTPS.

## 2. Что нужно сделать владельцу в Telegram

1. Войти в отдельную тестовую сеть Telegram: Desktop → Settings → Shift+Alt+правый клик по Add Account → Test Server. Создать отдельную тестовую учётную запись и нового бота через BotFather именно в тестовой сети. [Официальная инструкция](https://core.telegram.org/bots/webapps#testing-mini-apps). Существующего production-бота не изменять.
2. Приватно записать токен в `telegram/.env`, оставить `TELEGRAM_ENV=test`. Указать рабочий `SUPPORT_CONTACT`. Для проверки owner указать числовой ID своего аккаунта в этой тестовой сети; ID production-аккаунта не следует автоматически считать тестовым ID. Не публиковать значения.
3. После готовности публичного тестового origin указать его в `PUBLIC_ORIGIN`. Проверить настройки без изменений: из `telegram/` выполнить `node --env-file=.env setup-bot.cjs`. Для нового тестового бота применить `--apply`: установятся тестовые webhook, меню и /paysupport. Скрипт использует `/test/` при TELEGRAM_ENV=test. Main Mini App задать в настройках **этого нового** бота через BotFather.
4. Для тестов магазина включить `STARS_ENABLED=1` только на тестовом стенде. Платежи официальной тестовой сети отделены от production. Пройти создание invoice → pre_checkout_query → successful_payment → восстановление на другом тестовом клиенте → refund; сохранить обезличенные результаты. [Telegram Stars](https://core.telegram.org/bots/payments-stars). Подготовить доступные пользователю условия покупок и рабочую поддержку до публичного выпуска.

Реальные production-списания, возвраты и настройка действующего бота требуют отдельного разрешения и здесь не выполняются.

Для возврата **уже подтверждённого тестового** заказа подготовлен helper. Из `telegram/`, только с TELEGRAM_ENV=test и тестовой базой:

```sh
node --env-file=.env test-refund.cjs --apply-test-refund <TEST_ORDER_ID>
```

Он берёт пользователя и charge из подтверждённого заказа в SQLite, вызывает официальный refundStarPayment через `/test/` и ждёт настоящего refunded_payment для отзыва права. Производственный режим отвергается, локальные фиктивные возвраты не создаются, ID/токены не печатаются. Без флага операция не выполняется. Этот helper проверен автоматически с fixture API, но реальный тестовый возврат остаётся BLOCKED до появления бота/стенда.

## 3. Отдельный публичный тестовый HTTPS-origin

Нужны отдельный тестовый хост/изолированная VM, Docker Compose, домен и DNS A/AAAA на этот хост. Предоставленный доступ к существующим серверам отсутствует. Health существующего OnlineVDS отвечает, но он обслуживает другую версию и не используется для установки без разрешения. Порты 80/443 ниже предназначены для отдельного тестового хоста, не для замены существующего reverse proxy.

На тестовом хосте получить текущую ветку PR. Приватный `.env` перенести защищённо, не через Git; задать `STAGING_DOMAIN`, `PUBLIC_ORIGIN=https://<STAGING_DOMAIN>`, тестовый токен, поддержку и OWNER_TELEGRAM_ID. Затем из корня:

```sh
docker compose --env-file telegram/.env -f telegram/staging/compose.yaml config --quiet
docker compose --env-file telegram/.env -f telegram/staging/compose.yaml up -d --build
```

Используется отдельный project manager-telegram-staging, отдельные volumes баз, копий и TLS. Caddy получает сертификат для отдельного домена, приложение доступно через него; порт приложения наружу не публикуется. AdsGram принудительно OFF. Docker-образ исключает .env, приватные локальные файлы, базы, исходный архив и node_modules.

Проверить HTTPS `/health`: environment=test, starsConfigured соответствует флагу и поддержке. Health — проверка локальной конфигурации, не удостоверение успешного обмена с Telegram. Проверить настоящий вход через Mini App, 2–6 участников, устройства и приёмочную матрицу. В этой рабочей среде Docker отсутствует: compose подготовлен, но запуск контейнеров/ACME остаётся BLOCKED до доступа к хосту и DNS.

## 4. Копии и обновление

Базы содержат финансовые/персональные данные. Каталоги копий должны быть приватными и храниться дополнительно вне хоста. Хеши manifest выявляют повреждение; не подтверждают доверенность копии от неизвестного источника.

```sh
node telegram/backup-set.cjs snapshot /PRIVATE/DATA /PRIVATE/BACKUPS
node telegram/backup-set.cjs restore /PRIVATE/BACKUPS/snapshot-XXXX /PRIVATE/NEW-DATA
```

Создаются telegram.sqlite, rooms.sqlite и manifest с SHA-256, integrity_check и foreign_key_check. Online snapshot каждой базы допустим, но для согласованной точки отката **остановить записи/тестовый сервис на время снимка обеих баз**. Не копировать работающие SQLite только через cp, не забывать WAL. Восстановление допускается исключительно в новый отсутствующий каталог, живые данные не перезаписываются. Тестом проверены настоящая комната с ходом, покупки, профиль, owner и повтор команды после восстановления обеих баз.

В контейнерном контуре `/data` и `/backups` — отдельные постоянные volumes; скрипт доступен как `/app/telegram/backup-set.cjs`. Копии из volume дополнительно выгружать защищённо с хоста. До обновления сохранить SHA кода, manifest и приватную конфигурацию. Обновлять только выбранный стенд; существующие volumes не удалять.

Для отдельного Linux-стенда подготовлены `staging/manager-staging-backup.service` и `.timer`: ежечасный online snapshot с приватной umask. Перед установкой задать реального оператора в User и абсолютный путь checkout в WorkingDirectory; оператор должен иметь доступ к этому Docker-проекту. Установить шаблоны в `/etc/systemd/system`, выполнить daemon-reload и enable --now **только тестового timer**. Сначала вручную запустить oneshot и проверить manifest/restore в новом каталоге, затем контролировать list-timers и журнал задачи. В этой Windows-среде systemd не запускался. Автоматическое удаление копий не настроено: нужны согласованная политика хранения, контроль места и отдельная внешняя копия.

## 5. Откат

1. Остановить только тестовый сервис нужного compose project, сохранить снимок текущих данных для расследования.
2. Подготовить отдельно прежнюю проверенную ревизию кода и образ. Не выполнять reset --hard в рабочем каталоге пользователя.
3. При откате **кода** сначала сохранить текущие данные и, если схема обратно совместима, использовать текущие базы с прежним образом. Нельзя слепо возвращать старую финансовую базу: это потеряет покупки и возвраты после снимка. Восстановление старой пары допускается в закрытом контуре без более поздних транзакций либо после отдельной сверки и восстановления недостающих финансовых записей по Telegram/сохранённым журналам. Восстанавливать только в **новый** каталог; менять путь данных/volume только тестового сервиса, исходный набор оставить нетронутым.
4. Запустить прежний образ с его совместимыми настройками среды и новым восстановленным каталогом; проверить health, вход, покупки/owner и существующую комнату до открытия доступа игрокам.
5. Если проверка не прошла, сервис оставить закрытым, сохранить оба набора данных; не удалять и не обнулять их.

Автоматический snapshot/restore проверен локально. Реальный откат контейнерного стенда/production не проводился без доступа и разрешения. Локальные партии хранятся отдельно в аккаунтном localStorage, PeerJS checkpoint — в IndexedDB/экспорте. Они не становятся серверными облачными сохранениями от копирования SQLite; постоянные покупки и серверные комнаты находятся в SQLite.
