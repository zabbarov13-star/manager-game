# AdsGram: состояние и подключение

Проверено 18.11.2026 по официальным источникам. Статус реального rewarded-потока: **BLOCKED**, `ADS_VERIFIED_GATEWAY_ENABLED=0`.

## Что подтверждает документация

[Reward URL](https://docs.adsgram.ai/publisher/get-block-id) описан как HTTPS GET с Telegram userId. Уникальное ID завершённого просмотра, подпись, привязка к нашему intent и правила повторной доставки в этом контракте не документированы. Поэтому из него нельзя вывести требуемую защиту от повторной выдачи между последовательными просмотрами. Это вывод о достаточности опубликованного контракта; не утверждение, что провайдер не может предложить отдельную интеграцию.

[SDK API](https://docs.adsgram.ai/publisher/api-reference) возвращает клиентский результат show() и события onReward. Debug-показ не вызывает Reward URL. Эти сигналы не являются серверным доказательством. Код приложения теперь также проверяет done/error и отменяет незавершённое намерение.

Проверены официальные альтернативы: [Task Ads](https://docs.adsgram.ai/publisher/task-integration-example) документируют браузерное событие reward; [Bot Ads](https://docs.adsgram.ai/bots/create-block) используют пару click_url/reward_url после клика, а не требуемый поток просмотра видео в Mini App. Публично описанной замены с нужными гарантиями в этих механизмах не найдено. Мы не подменяем добровольный просмотр кликовым заданием.

## Что уже готово

Добровольная кнопка, загрузка SDK по действию пользователя, намерение на выбранный товар, отмена, ожидание серверного подтверждения, SQLite-права, общий лимит 3/сутки на ID, сброс в 00:00 МСК, +24 часа и потолок 72 часа. Повтор receipt не выдаёт награду; клиент API выдачи не имеет. Постоянное право приоритетно, истечение временного не меняет уже начатую партию. Автотесты используют внутренние подписанные fixture-receipt и не объявляются реальной рекламой.

`POST /ads/verified-receipt` остаётся внутренним HMAC-контрактом. Это не нативный endpoint AdsGram и его нельзя просто вставить в Reward URL. Адаптер пока намеренно не реализован: неизвестен доверенный входной протокол, который ему предстоит проверять.

## Действия владельца

1. Зарегистрировать publisher-кабинет на [partner.adsgram.ai](https://partner.adsgram.ai/registration). Создать Telegram Mini-app platform с адресом отдельного тестового стенда и ссылкой на тестового бота. Для разработки выбрать Test platform согласно официальной инструкции; тестовые показы не являются подтверждением боевой награды.
2. Создать блок типа **Reward**, получить Block ID через Show code и сохранить только в приватном `.env`: `ADSGRAM_BLOCK_ID=...`. Оставить `ADS_VERIFIED_GATEWAY_ENABLED=0`.
3. Через кабинет или [официальную поддержку](https://docs.adsgram.ai/bots/create-block) запросить серверное подтверждение rewarded completion. Подготовленный текст запроса ниже; автоматически он никому не отправлялся.
4. Получить письменную спецификацию/официальное согласование и тестовый доступ. После этого реализовать адаптер, проверить подлинность, уникальность и повторную доставку, затем выполнить реальный тест со стендом. Только после этого включать выдачу. Сам по себе Block ID эту зависимость не закрывает.

Текст для поддержки:

> Для Telegram Mini App нужны временные косметические награды за rewarded video. Предоставляете ли вы серверное подтверждение завершённого просмотра с уникальным неизменным event/transaction ID, проверяемой подписью либо серверным verify API, Telegram ID, Block ID, временем и привязкой к переданному intent/nonce? Нужны правила повторной доставки, проверки давности и способ тестирования. Опубликованный Reward URL содержит только userId; его недостаточно для однократной выдачи при нескольких просмотрах подряд. Просим прислать официальный контракт и доступный тестовый механизм.

Никакие клиентские токены, статический секрет в доступном пользователю URL или самостоятельно придуманные заголовки провайдера не будут считаться таким подтверждением.
