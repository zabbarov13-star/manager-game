# Тест онлайн-комнат «Менеджера»

В тестовой сборке обычные комнаты обслуживает Node.js по HTTP(S). Игровые правила и проверки взяты из исходной 0.19.0. Сервер хранит комнаты, ключи участников в виде хешей и подтверждённое состояние в SQLite. Каждый вход проксирует запросы к одному авторитетному серверу. Render и WebRTC не нужны для новых комнат. Старые комнаты PeerJS доступны в разделе диагностики. Сохранения 0.19.0 и опубликованный Pages не изменяются.

## Запуск

Из корня репозитория с Node.js 24:

```sh
node online/generate.cjs
node online/server.cjs
```

Откройте http://127.0.0.1:8080/ на ПК. Для готового архива CI выполните только вторую команду из каталога, где находится распакованная папка online. Сервер пишет в data/rooms.sqlite. Для локальной проверки двумя устройствами используйте HTTPS-прокси к серверу. Для проверки разных сетей нужен внешний HTTPS-адрес, доступный обоим устройствам. Открывать порт Node в интернет напрямую не требуется.

## Отдельная тестовая инфраструктура

1. На независимом от Render хосте с постоянным диском запустите один сервер. Контейнер можно собрать командой `docker build -f online/Dockerfile -t manager-online .`. Монтируйте постоянный том в /data. Открывайте сервис через HTTPS-прокси и проверяйте /health. Без постоянного диска перезапуск контейнера может уничтожить партии.
2. Для резервного входа настройте второй HTTPS-прокси на независимой сети. Оба прокси ведут в тот же процесс и к той же базе, сохраняют URL и заголовки Authorization и Idempotency-Key, отключают кэш для /api/. Для канала между прокси и приложением используйте защищённое соединение. Два самостоятельных контейнера с разными томами создадут две разные системы комнат.
3. Задайте `ROOM_ENTRANCES=https://backup.example.org` при генерации клиента или через одноимённый аргумент Docker build. Задайте `ROOM_ALLOWED_ORIGINS=https://test.example.org,https://backup.example.org` процессу Node. Укажите реальные HTTPS-адреса, без завершающего слеша. При отсутствии резервного адреса клиент использует тот же домен, с которого загружена игра.
4. Ограничьте объём и частоту запросов на периметре, исключите токены и заголовок идемпотентности из журналов, настройте резервное копирование SQLite с учётом WAL. Проверьте восстановление из копии. Храните файлы базы и резервные копии закрытыми.
5. Зафиксируйте отдельно доступность страницы и каждого входа. Если сама страница недоступна при первом открытии, нужен доступный URL для загрузки. Если недоступен авторитетный сервер или постоянный диск, оба входа будут недоступны до восстановления. Это резервирование пути доступа, а отказоустойчивость самой базы требует отдельной инфраструктуры.

Переход между входами происходит автоматически при сетевой ошибке или временном отказе прокси. У запроса ограничен бюджет времени. Запись и квитанция HTTPS-запроса фиксируются вместе. Для действий движок дополнительно проверяет идентификатор команды, участника и ревизию. После разрыва активная сессия повторяет запросы. После перезапуска она восстанавливается с того же браузера и профиля, где сохранён ключ. Уход создателя не выключает сервер. В партии действуют прежние правила таймера, а запуск ещё не начатой партии остаётся за создателем.

## Физическая проверка

- На ПК или телефоне хоста откройте отдельный тестовый URL. Создайте стол, скопируйте ссылку и откройте её на проблемном телефоне без VPN. Второй игрок вводит имя и нажимает «Занять место». Проверьте, что оба видят один код и два имени.
- Отметьтесь готовыми, начните партию, сделайте несколько ходов. Сверьте кубики, очередь, деньги и имущество. Повторите с проблемным телефоном в роли хоста.
- На устройстве гостя выключите сеть во время действия, затем включите мобильный интернет. Проверьте, что ход записан один раз. Закройте и снова откройте игру в том же браузере. Закройте вкладку создателя и проверьте, что состояние доступно гостю.
- Повторите для Android Chrome и установленного APK, iPhone Safari и PWA, iPad Safari/PWA, Windows. Приложения 0.19.0 используют свои существующие маршруты. Для проверки этой схемы в APK и IPA нужны отдельные тестовые сборки с тестовым URL.
- Зафиксируйте платформу, типы сетей, этап сбоя и состояние двух экранов. Уберите токены и ссылки-приглашения из отчёта. Приёмка на проблемном телефоне обязательна перед выпуском.

Автоматические проверки выполняются в GitHub Actions. Тест с настоящими HTTP-сокетами моделирует отказ входа, потерянный ответ после записи, повтор и перезапуск с той же базой. Два браузерных контекста проверяют приглашение, общую партию и восстановление. Физические сети и доступность конкретного внешнего хоста проверяются отдельно.

Для отдельного бесплатного публичного теста см. [настройку alwaysdata](FREE-HOST-RU.md).

Отдельный пакет для бесплатного облачного хоста описан в [инструкции Johnny](JOHNNY-RU.md).
